## 5. 浇水门结果（真实数据 + 逐点破坏）

- 基线（真实接口）→ `strong`，口径"三个点位今天的绝对含水率读数都低于各自最近一周的均值（今天 9.4/6.8/8.7%）…建议适当补水"
- 缺时间 / 格式错 / 未来 / 过期（单点）、2 点缺时间 → cautious，口径改为"这组读数里有 N 个点位的时间戳异常（…），不能作为强建议依据；先核实读数时间或现场看墒情"
- 三点全缺 / 三点全 0 / 三点完全相同 → `invalid`
- 乱序 → 按时间戳取最新；趋势按 `deviceNum` 对齐、基线为最近一周（未改动）
- 降雨：≥50%（阈值不变）→ level 与口径同步降级为 cautious，不再出现"strong + 先看雨情"矛盾

## 8. 部署安全移交（只读审计，未做任何修改）

**已核实事实**：
1. 34 个 HTTP 节点全部 no-auth，且全部为明文 `http://`（0 个 https），基址如 `http://47.120.32.59:8080/ai/data/*`、`http://47.120.32.59:8000/detect`。
2. 无任何鉴权头即可 `GET /ai/data/bases`、`/ai/data/yield` → 200。
3. `GET /ai/memory?userId=8` 在无任何身份凭证下返回 200，可读到其它 userId 的记忆（只统计条数=3，未读取内容）⇒ userId 可枚举、接口与会话身份未绑定。
4. `https://47.120.32.59:8080` 不可用（该端口仅明文）⇒ 工作流侧当时没有等价 HTTPS 通路。
5. 涉及用户记忆的节点：`HTTP：取用户记忆` / `HTTP：写用户记忆`（均 no-auth + 明文）。

**尚未核实（需后端/运维确认）**：是否有访问白名单 / 内网隔离 / 网关鉴权；正式部署是否走 HTTPS 或等效传输；日志中是否留存敏感响应内容。

**后端负责人待办（建议）**：① 给 `/ai/memory` 与写入类接口加身份绑定 + 鉴权（至少禁止仅凭 `userId` 读取他人记忆）；② 提供 HTTPS 或网关层终止 TLS；③ 确认是否存在访问白名单/内网隔离；④ 明确 userId 与会话的绑定方式。

> 后续进展（截至 2026-10-10）：工作流侧 33 个数据接口节点已统一携带内部调用密钥，后端已启用强制校验，鉴权部分已完成主体收口；userId 与会话绑定等仍在路线图。本节为当时快照，另附一行后续进展，未改写历史结论。
