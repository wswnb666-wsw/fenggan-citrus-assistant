## 一、一句话概述

**丰柑智农助手**是面向**柑橘种植户**的农业问答智能体：农户用自然语言问果园的实时数据、病虫害、用药安全、农事安排、产量销售等问题，系统**先从本园真实数据/权威知识库里取证据，再由确定性代码做判断，最后才让大模型组织成人话回答**。

**核心理念一句话**：**事实、计算、资格判断、安全门禁交给代码；解释、组织语言、自然表达交给大模型。**

## 三、整体架构（分层看）

```
① 入口与准备
   用户输入（可带图片）
   → 获取今天日期 → 有没有传图片？ → HTTP：取用户记忆 → 规则/条件：要不要提取记忆？
   → 记忆净化：改写用 → 问题改写（LLM）→ 取基地名 → 查询天气 → 整理天气

② 主干（所有分支共用）
   → HTTP：证据门-病虫害记录 → HTTP：证据门-用药记录 → 【证据门：用药决策】(确定性)
   → 前置规则：病虫害处置？（确定性） → 前置路由：症状/钱（确定性）

③ 分流（确定性路由优先，分类器兜底）
   ├─ 多意图通道（一句话问了两类以上数据 → 一次取齐 9 路数据 + 2 个知识库）
   ├─ 虫情现状 / 症状 / 趋势 / 天气 / 泛问 / 浇水 / 间隔期安全 / 钱 / 农事 / 产量 / 地块品种（各定一条分支）
   └─ 以上都不中 → 问题分类器（13 类）→ 对应分支

④ 各分支取证
   HTTP 数据接口（实时读数/记录/台账）+ 知识检索（权威知识库）+ 确定性门（证据门/浇水门/自检）

⑤ 回答生成与清洗
   各分支 LLM 生成 → 【清洗回答：××回复】(17 个确定性清洗节点) → 对应答复节点

⑥ 记忆写回
   LLM：记忆提取 → 清洗记忆 JSON → HTTP：写用户记忆
```

**为什么在主干上先放"证据门"**：任何分支（包括多意图）只要涉及"要不要用药"，都必须在取数之后立刻拿到一个**确定性的安全结论**，再交给 LLM 组织语言。

## 四、功能模块逐个说明

### 1. 多轮记忆（读 / 写）
- 读：主入口后立刻 `HTTP：取用户记忆`（含用户档案：品种、地块、基地）+ `条件：要不要提取记忆？`
- 写：对话结束后由 `LLM：记忆提取` 抽取值得长期记住的事实 → `清洗记忆 JSON` → `HTTP：写用户记忆`
- **记忆净化**（`记忆净化：改写用`）：把"含病虫名"的记忆条目**从改写视野里摘掉**，防止把历史病名（如"东区苗圃溃疡病反复"）当成这一轮的对象。

### 2. 问题改写（LLM）
把口语化问题变成完整问句，并遵守硬规则：
- **对象继承**：用户说"那个/它"时，从上一轮补全对象（"那个要不要打药？"→"红蜘蛛要不要打药？"）
- **不臆造**：用户原话已完整时原样返回；不许把现状问句改成知识问句
- 改写结果只用于"检索/匹配"，**关键判断仍然用用户原话兜一道**（见下）。

### 3. 确定性前置路由（16 个 if-else + 1 个 code 节点）
**路由优先级**（先命中先走，全部由代码判断，不靠模型）：

> 多意图（虫情+用药）> 浇水决策 > 多意图（通用）> 虫情现状 > 症状类 > 虫情（只提名）> 趋势（过去时间词）> 天气 > 趋势（泛问/环境读数）> 泛问"地里怎么样" > 浇水类（知识向）> 多意图（对象待确认）> 间隔期/采果安全 > 钱 > 农事 > 产量 > 地块/品种 > **都不中 → 分类器**

**双层词表**：`前置路由` 负责"往哪走"，`证据门` 负责"能不能被执行"。
两份词表**同时检查"用户原话"和"改写结果"**——实测过事故：改写把"要不要打药"变成"间隔期问了吗"，只查改写结果就会丢掉决策意图。

### 4. ★ 用药决策证据门（本项目最核心的安全设计）
**输入**：用户原话、改写问题、病虫害记录、用药记录 → **输出**：`decision_level` + 一句"必须照抄"的结论句。

| 等级 | 触发条件 | 允许的回答 |
|---|---|---|
| **strong** | 近 7 天有该病虫实时记录且识别数 ≥ 3 + 病虫在词表 + **安全间隔期已满** + **本轮知识库确有该病虫防治资料** | 才允许"可以按防治指标安排用药"这类执行级结论 |
| **insufficient** | 有记录但不足 / 间隔期未满 / 知识库无依据 / 时间戳异常 | 只能"先巡查确认虫情，再决定是否用药" |
| **invalid** | 对象不明 / 数据接口异常 / 记录格式异常 | 先澄清对象或先检查设备 |

**四道防线（同一红线层层兜底）**：
1. **代码判级**：等级由代码算，不看模型脸色；
2. **口径硬保证**：非 strong 时，清洗节点**用代码把结论句放到第一句**（不依赖模型"照抄"）；
3. **执行级句子删除**：正文里出现"建议补防/适合喷药/可以再打/是否采取防治措施"等**正向执行动作**整句删除，否定句/事实句/条件句保留（含转折子句独立判定）；
4. **决策词查原话**：改写换说法也丢不掉"要不要打药"这个意图。

**对象一致性**：病虫名做别名归一化（介壳虫↔蚧壳虫、沙皮病↔砂皮病、锈蜘蛛↔锈壁虱、柑橘木虱↔木虱），用户原话、实时记录、用药记录、知识库匹配**用同一套归一化**；无法识别时保守降级、绝不猜。

### 5. ★ 安全间隔期（农药采收安全）
- **一律由代码计算**（`算安全间隔` / `算安全间隔（现在）`）：施药日 → 已过 N 天 → 还差 N 天 → 是否已达到；**绝不让模型自己算**；
- 冲突时**取较大值**（更保守），以农药标签为准；
- 用药记录接口异常、字段缺失或非法、病虫名无法识别 → **一律"不能确认"，不得判定为合格**（安全门不允许乐观默认）。

### 6. ★ 浇水建议强度门
`water_advice_level` 三档，全部由代码定：

| 档位 | 条件 | 允许的表达 |
|---|---|---|
| **strong** | 三个点位读数**都低于各自最近一周均值** + 点位一致 + 无异常 + **各点位时间戳均正常** | "建议适当补水" |
| **cautious** | 读数偏低但不满足强条件 / 有降雨概率 / 农户提到设备可疑 | "先结合田间实际确认" |
| **invalid** | 三点全 0 / 三点完全相同 / 全部过期或缺失 | "先检查探头" |

关键约束：土壤湿度是**绝对含水率**，**不套用 60%~80% 相对含水量标准**；任一参与点位**时间戳缺失/无法解析/在未来/已过期**都不许给强建议；**高降雨概率（≥50%）时门会同步降级**，避免"一边建议补水、一边又说先看雨情"。

### 7. 知识（权威知识库）
- 8 个检索节点，实际挂载 **4 个在用库**（见第七节）；
- 检索词由 `拼装检索词` 统一生成；
- **知识有效性双重校验**：必须同时满足"含本轮病虫名" **且** "含防治依据（药剂/稀释倍数/安全间隔/喷施等）"——只提名字、只讲发生规律、只给管理措施**都不算**知识支持（不通过则把 strong 降级）。

### 8. 天气
- 接口 `GET /ai/data/weather?base=<基地>`（自建后端，10 分钟缓存，数据源 Open-Meteo）；
- `整理天气` 把 JSON 压成纯文本，**显式按日期分组**：今天剩余时段 / 明天 / 后天 / 已过去；数据陈旧打 `⚠️`；
- 接口失败时**明确说"天气接口这次没返回数据"**，禁止拿气候常识当本园天气。

### 9. 多意图通道（一句话问多件事）
- 触发：一句话里问了两类以上不同数据（或"虫情 + 要不要用药"），且有明显分隔；
- 动作：**一次取齐 9 路数据**（实时环境、农事、物候、产量、销售、病虫害、用药、用药知识库、栽培知识库）→ `整理多意图数据` 压成约 2KB 结构化文本 → 综合 LLM 一次答完；
- 好处：农户一句话问三件事不必问三次；数据在代码里被裁剪聚合，避免大 JSON 塞爆上下文。

### 10. 图片识别（病虫害拍照）
- `HTTP：调用识别模型（病害+虫害）` → `http://47.120.32.59:8000/detect`，**一次调用同时返回病害与虫害结果**（含标注图 URL）；
- `解析识别结果` 把英文类别映射成中文检索词 → 检索防治知识库 → LLM 解读 → 清洗 → 答复；
- 图片地址由 `拼图片地址` 统一拼接，基址独立成一行便于切换。

### 11. 统一回复协议与清洗（17 个清洗节点）
每个分支的回答都要过一遍确定性清洗：
- **空回答兜底**：模型偶发返回空 → 给确定性文案，用户**永远看不到空白**；
- 去 markdown 符号、去内部标记（"（按规则要求…）"等 4 种形态）、去编号（且**防误伤小数**，`30.9℃` 不会被吃成 `30 9℃`）；
- **统一回复协议**（15 个回答节点共用）：先给结论 → 关键证据 → 判断 → 建议 → 必要时追问；不出现"追问："字样、不用 markdown 符号、标明数据时间与新鲜度。

### 12. 设备读数自检
`自检：读数异常`（代码）：只对**恒 0 / 三点完全相同 / 离线久未更新**报异常，输出 `finding` + `abnormal`（v90 起增加**三态**：不可判断时不硬报正常/异常）；
提示词里把自检结论设为**权威**，并明确"**读数偏低 ≠ 异常**，只有自检 abnormal=1 才允许说'先检查探头'"。

## 五、核心设计原则（写资料时的"卖点"）

| 原则 | 具体做法 | 举例 |
|---|---|---|
| **数据不编** | 所有本园数据都来自接口；接口失败就说"本次没取到" | 天气接口失败 → 明说没数据，不许凭常识猜 |
| **计算不交给模型** | 计数、统计、天数、资格判定全部代码算 | "还差 3 天过间隔期"由代码算，模型只照抄 |
| **资格判定是硬门禁** | 三档等级 + 固定结论句，代码保证第一句 | 证据不足时第一句必是"当前证据不足，先巡查确认虫情" |
| **保守优先** | 安全间隔取较大值；数据不可靠宁可降级；对象不明不猜 | 用药记录接口 500 → "暂不能确认安全间隔" |
| **口径可追溯** | 结论句由代码生成，界面上一眼可辨"系统已按硬证据判好" | 提示块标注 `decision_level` / `accuracy` 等字段 |
| **可解释** | 每个结论都带数据来源与时间 | "这是今晚 23:40 的读数" |

## 十、已知限制与后续（如实，写资料时建议不要写"完全没问题"）

1. **偶发空回答**：曾出现"我这边没有数据"式空回答，已定位到平台侧**知识库检索限流**（订阅级），应用侧已加重试 + 兜底文案，但**配额本身无法解决**；
2. **另有一类偶发空回答未复现**（找不到根因），继续观察；
3. **浇水/用药的"建议强度"门槛是工程阈值**，不等于农学防治指标（如"设备识别 ≥3 头算证据充分"是工程口径，实际用药还要看标签、知识库与当地农技意见）；
4. **知识库有效性判定**目前是"含病虫名 + 含防治依据"的启发式，尚未按"是否含具体药剂"细分；
5. **后端内部接口已加调用密钥校验**（`X-Internal-Token`，2026-10-09 起强制）；**业务入口仍为 8080 明文 HTTP**（HTTPS 域名入口受备案限制），更彻底的身份绑定仍在路线图中；
6. 天气接口只有未来约 12 小时逐时数据，**看不到后天**，回答里会明确说明并建议看手机预报。
