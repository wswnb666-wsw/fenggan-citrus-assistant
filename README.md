# 丰柑智农助手 · 柑橘智慧果园 AI 助手

> 面向柑橘种植户的农业问答智能体：农户用自然语言问果园的**实时数据、病虫害、用药安全、农事、产量销售**，
> 系统**先从本园真实数据与权威知识库取证，再由确定性代码做判断（安全门禁），最后才交给大模型组织成人话**。

本仓库是参赛作品《丰柑智农助手》的**工作流定义与设计说明**，与在线可运行程序配套提交：

| 交付物 | 链接 | 说明 |
|---|---|---|
| **可运行程序（在线演示）** | https://udify.app/chat/Xwj7SlLOEdf2ZNlY | 基于 Dify 发布的应用，点开即可对话 |
| **工作流源码（本仓库）** | 本页 | 工作流 DSL、设计说明、验收记录 |

> ⚠️ 本仓库提供的是**工作流定义（DSL）+ 设计文档**。工作流运行时所依赖的业务数据接口由我们**自建的后端服务**提供（不在本仓库内）；评审老师如需体验完整功能，请使用上表的**在线演示链接**。

## 一、这是什么

系统形态：**Dify Advanced Chat（对话型工作流）**，共 **134 个节点 / 153 条连线**。

```
① 入口与准备      用户输入（可带图片）→ 取用户记忆 → 记忆净化 → 问题改写 → 取基地名 → 查询天气 → 整理天气
② 主干门禁        → 取病虫害记录 → 取用药记录 →【证据门：用药决策】(确定性) → 前置规则 → 前置路由
③ 确定性分流      多意图 / 虫情现状 / 症状 / 趋势 / 天气 / 泛问 / 浇水 / 间隔期安全 / 钱 / 农事 / 产量 / 地块品种
                  （以上都不中才交给 13 类问题分类器）
④ 分支取证        HTTP 数据接口（实时读数/记录/台账/统计）+ 知识检索（权威知识库）+ 确定性门（证据门/浇水门/读数自检）
⑤ 生成与清洗      分支 LLM 生成 →【清洗回答：××回复】(17 个确定性清洗节点) → 答复
⑥ 记忆写回        LLM 记忆提取 → 清洗记忆 JSON → 写用户记忆
```

**节点构成**：37 个代码节点（确定性计算/门禁/清洗）、19 个 LLM 节点（统一 DeepSeek-V3）、34 个 HTTP 接口节点、
8 个知识检索节点（引用 4 个知识库）、16 个条件判断、1 个 13 类分类器、18 个答复节点。

## 二、核心技术点

### 1. 安全门禁由代码决定，不由模型"自觉"
用药决策走一条**确定性证据门**（`证据门：用药决策`），代码输出三档结论：

| 等级 | 触发条件 | 允许的回答 |
|---|---|---|
| **strong** | 近 7 天有该病虫实时记录且识别数 ≥ 3 + 病虫在词表 + **安全间隔期已满** + **本轮知识库确有该病虫防治依据** | 才允许"可以按防治指标安排用药" |
| **insufficient** | 有记录但不足 / 间隔期未满 / 知识库无依据 / 时间戳异常 | 只能"先巡查确认虫情，再决定是否用药" |
| **invalid** | 对象不明 / 接口异常 / 记录格式异常 | 先澄清对象或先检查设备 |

配套**四道防线**：① 代码判级 → ② 口径硬保证（非 strong 时由代码把结论句放到回答第一句，不依赖模型"照抄"）
→ ③ 执行级句子删除（正文里"建议补防/适合喷药/可以再打"等正向执行动作整句删除，否定句/事实句/条件句保留）
→ ④ 决策意图同时检查**用户原话**与改写结果（防止改写换说法丢掉意图）。

**v89–v96 后续加固**：执行决策词表**三处同补**、判定升级为**分句级**与**两线判据**、图片分支套用同等门禁、清洗豁免改为**条件组合**（详见第五节版本表）。

### 2. 安全间隔期（农药采收安全）一律由代码计算
`算安全间隔` / `算安全间隔（现在）` 两个代码节点负责：施药日 → 已过 N 天 → **还差 N 天** → 是否已达到；
冲突时**取较大值**（更保守）；**绝不让模型自己算日期差**。
用药记录接口异常、字段缺失或非法、病虫名无法识别 → 一律"**不能确认**"，不允许默认合格。

### 3. 浇水建议强度门
`water_advice_level` 三档（strong / cautious / invalid），依据：三点位读数与**各自最近一周均值**的关系、
点位一致性、异常检测（全 0 / 三点相同 / 过期缺失）、**逐点位时间戳完整性**。
明确约束：土壤湿度是**绝对含水率**，不套用 60%~80% 相对含水量标准；高降雨概率时门会**同步降级**，避免"一边建议补水、一边又说先看雨情"。

### 4. 多意图：一句话问多件事，一次取齐
当一句话问了≥2 类不同数据时，走多意图通道：**一次取齐 9 路数据**（实时环境/农事/物候/产量/销售/病虫害/用药/用药知识库/栽培知识库）
→ 代码压缩成约 2KB 结构化文本 → 综合 LLM 一次答完。避免大 JSON 塞爆上下文，也避免农户问三遍。

### 5. 数据可信度
- 设备读数自检（`自检：读数异常`）只对"恒 0 / 三点完全相同 / 离线久未更新"报异常；**读数偏低 ≠ 异常**；
- 天气按「今天剩余时段 / 明天 / 后天 / 已过去」显式分组，**禁止跨日张冠李戴**，接口失败就明说没有数据；
- 病虫名做**别名归一化**（介壳虫↔蚧壳虫、沙皮病↔砂皮病、锈蜘蛛↔锈壁虱、柑橘木虱↔木虱），
  用户原话、实时记录、用药记录、知识库匹配用同一套归一化；无法识别时保守降级、绝不猜。

## 四、如何复现（导入 Dify 运行）

1. **准备 Dify**：任意 Dify 1.x 环境（云版或自建）。
2. **导入工作流**：`工作室 → 创建应用 → 导入 DSL 文件`，选择 `workflow/fenggan-workflow-v99.yml`。
3. **配置模型**：工作流内 19 个 LLM 节点统一使用 **DeepSeek-V3**（示例走 `langgenius/siliconflow` 供应商）。
   导入后请在「模型供应商」里配置你自己的 Key，并在各 LLM 节点重新选择模型。
4. **挂载知识库**：工作流引用 4 个知识库（柑橘知识库 / 病虫害防治 / 科学用药与安全间隔期 / 物候期管理）。
   仓库不含知识库内容，可用你自己的柑橘资料新建 4 个知识库后重新挂载（步骤：编辑「知识检索」节点 → 选择数据集）。
   知识库内容取自公开权威来源（各级农业农村部门发布资料），本项目做了结构化整理。
5. **配置数据接口**：工作流含 34 个 HTTP 节点，指向我们自建的后端服务（`/ai/data/*`：天气、传感器、病虫害记录、
   用药记录、物候、农事、产量、销售、虫情设备、用户记忆；`/detect`：病虫害图像识别）。
   评审老师如需完整体验，建议直接使用上文的**在线演示链接**。
   说明：工作流内 33 个 HTTP 节点带 `X-Internal-Token` 调用头，仓库版已统一脱敏为占位符 `<YOUR-INTERNAL-TOKEN>`；如你自建后端，请替换为你自己的密钥（或去掉该头）。
6. **发布**：`发布 → 更新`，即可在「探索」或 WebApp 页面与助手对话。

## 七、已知限制（如实说明）

1. 业务数据接口为自建服务，仓库不含后端实现；本仓库主要提供工作流与设计文档；
2. 知识库检索受平台订阅配额限制，偶发限流已通过重试 + 空回答兜底缓解，配额本身无法解决；
3. "证据充分"阈值（如设备识别 ≥3 头）是**工程门槛**，不等同于农学防治指标；实际用药仍需依据农药标签、
   知识库与当地农技意见；
4. 天气接口只覆盖未来约 12 小时逐时数据，看不到后天，系统会明确说明并建议参考手机预报；
5. 后端内部接口已启用**调用密钥校验**（`X-Internal-Token`，2026-10-09 起强制）防止公网裸读；但业务入口暂为 8080 明文 HTTP（HTTPS 域名入口受备案限制），更彻底的身份绑定（userId 与会话绑定）仍在路线图中。

## 八、如何更新本仓库

工作流每次迭代后，用仓库根目录的脚本一条命令同步（脚本会：导出最新 DSL → 提交 → 推送）：

```bash
# 用法：把 GitHub Token 作为参数传入（用完请在 https://github.com/settings/tokens 撤销）
bash publish.sh <github_token> [提交说明]
```

- 脚本会自动从 Dify 导出**当前已发布版本**的 DSL 到 `workflow/fenggan-workflow-v<版本号>.yml`
  （按线上版本号自动命名、旧版本文件自动清理；导出需要本机已登录 Dify 的浏览器会话；若不可用，脚本会跳过导出、只提交现有文件）；
- 导出时会自动把 `X-Internal-Token` 的真实取值替换为占位符 `<YOUR-INTERNAL-TOKEN>`，**仓库不携带任何真实密钥**；
- 也可以手动推送：`git add -A && git commit -m "..." && git push`（需要提供凭据，或用 GitHub Desktop 图形客户端）。
